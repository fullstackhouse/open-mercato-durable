# Releasing

Automatic. Every merge to `main` that changes something a user can see is released: the version
comes from the conventional commits since the last tag, both packages publish at that version,
and the tag, GitHub release and changelog are written from the same commits. A merge of only
`chore`/`docs`/`refactor`/`test` commits releases nothing.

    fix:      → patch     feat:     → minor     feat!: / BREAKING CHANGE: → major

## Why one version for two packages

They are not independent things that happen to share a repo. The mirror is generated against a
pinned `@open-mercato/core`, the compat probe asserts the seams the adopter decorates, and the
harness exercises both. A change to either is only ever validated against the other, so shipping
them at drifting versions would invent a combination nothing has run.

`scripts/set-release-version.mjs` also rewrites the adopter's dependency on the mechanism to
`^<version>`, so that range stays honest without anyone remembering it. Yarn still links the
workspace locally, because the workspace version satisfies the range.

## Authentication

npm **trusted publishing** over OIDC — no token is stored anywhere. The workflow requests an
identity token from GitHub, npm verifies it against the publisher configured for the package,
and the published artifact carries provenance.

## One-time setup, per package

npm cannot create a package over OIDC: a trusted publisher can only be configured on a package
that already exists ([npm docs](https://docs.npmjs.com/trusted-publishers/)). So each package
needs one manual first publish, and then never again:

Both packages are already at `0.1.0`, with the adopter's peer range pinned to match, so the
bootstrap is only the publishing — and it is a script:

```bash
npm login --auth-type=web --scope=@fullstackhouse
./scripts/bootstrap-release.sh
```

It publishes the mechanism, then the adopter, hands publishing rights to CI with
`npm trust github`, tags `v0.1.0`, and sets `NPM_RELEASE_ENABLED`. After each publish it asks the
registry whether the package is really there, rather than trusting the exit code. After each publish it asks
the registry whether the package is actually there, rather than trusting the exit code. It checks the working tree
and runs the install lane first — a version number can never be reused — and every step is
skipped if it has already happened, so re-running it is safe.

**It has to be run from a terminal you can see.** npm masks the 2FA approval URL in both its
output and its debug log, deliberately, so neither the publish nor the trust configuration can
be driven by a script or an agent that cannot read your screen. Each of the two publishes and
each of the two trust calls will ask you to approve in the browser.

If the trust step is more trouble than it is worth, the same thing can be set on npmjs.com:
each package's page → *Settings → Trusted publisher* → GitHub Actions, repository
`fullstackhouse/open-mercato-durable`, workflow `ci.yml`. The script skips any package that is
already configured, so doing it in the browser and re-running is fine.

Two details it handles that are easy to get wrong by hand:

- **`--no-provenance` on these two publishes only.** Provenance is generated by the CI provider
  and cannot be produced from a laptop, so `publishConfig.provenance: true` — which is exactly
  what every automated release should use — makes a manual publish fail outright. Note the
  spelling: `--provenance=false` parses as the boolean flag plus a stray positional, and npm
  then exits 0 having published nothing.
- **The mechanism publishes first.** The adopter peer-depends on `^0.1.0`, and a peer range that
  cannot be satisfied is a broken install for anyone who takes the adopter alone.

From then on every merge to `main` publishes by itself.

Step 6 is not optional bookkeeping. Verified against this history: with no tag on the branch,
semantic-release computes the first release as **1.0.0**; with `v0.1.0` present it picks up from
0.1.0 and releases nothing until a `feat` or `fix` lands. The tag is what keeps the line in 0.x.

Step 7 is why the pipeline is green in the meantime. Until each package exists on npm, an
automated release could only fail, and a permanently red pipeline is how people learn to ignore
one.

## Checking what a merge would release

    yarn release:dry-run

Reports the version it would pick and the notes it would write, and publishes nothing.

## The trusted-publishing 403, and what it actually was

Publishing is npm trusted publishing: no stored credential, CI minting one per publish from its
OIDC identity. Getting there took several failed releases, and the last failure is worth
recording because it points squarely at the wrong thing.

The first two were ours: `npm version` could not parse yarn's `workspace:` protocol, and
`prepack: yarn build` re-entered yarn's resolver after the version bump had staled the lockfile.
The third reached the registry:

    npm error code E403
    npm error 403 Forbidden - PUT .../open-mercato-durable-work
              - OIDC permission denied for this action

That reads like a misconfigured trusted publisher. It is not one — and the run said so, if you
read it closely: earlier, for both packages, `OIDC token exchange with the npm registry
succeeded`. A probe job confirmed the claims are right: run from `ci.yml` the exchange returns
**201 with a token**, run from any other workflow file it returns **404 "package not found"**,
including for `@fullstackhouse/cerber` where trusted publishing demonstrably works. A plain
`npm publish` from the same job reproduced the 403 with semantic-release out of the picture, so
the release tooling was never implicated.

**What it was: a trusted publisher allows *staged* publishing by default, and nothing else.**
The package settings carry an "Allowed actions" choice — `npm stage publish` is always allowed,
and "Allow `npm publish`" is a separate checkbox that is off unless someone ticks it. Until it is
ticked, a direct publish is refused. So the error is precise rather than misleading: the
publisher was trusted, and the *action* was not permitted. npm labels ticking it "not
recommended", preferring staged publishing with a human promoting the release — a trade-off
worth knowing about if this pipeline is ever revisited.

Each failed attempt left a `chore(release)` commit and a `v0.1.1` tag behind, because
semantic-release tags before it publishes. The tags were deleted so 0.1.1 is still the next
version to go out; the commits are harmless and were kept.
