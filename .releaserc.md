# Releasing

Automatic. Every merge to `main` that changes something a user can see is released: the version
comes from the conventional commits since the last tag, both packages publish at that version,
and the tag, GitHub release and changelog are written from the same commits. A merge of only
`chore`/`docs`/`refactor`/`test` commits releases nothing.

    fix:      → patch     feat:     → minor     feat!: / BREAKING CHANGE: → major

## Why one version for two packages

They are not independent things that happen to share a repo. The mirror is generated against a
pinned `@open-mercato/core`, the compat probe asserts the seams the adopter decorates, and the
harness exercises both. A change to either is only ever validated against the other, so shipping
them at drifting versions would invent a combination nothing has run.

`scripts/set-release-version.mjs` also rewrites the adopter's dependency on the mechanism to
`^<version>`, so that range stays honest without anyone remembering it. Yarn still links the
workspace locally, because the workspace version satisfies the range.

## Authentication

npm **trusted publishing** over OIDC — no token is stored anywhere. The workflow requests an
identity token from GitHub, npm verifies it against the publisher configured for the package,
and the published artifact carries provenance.

## One-time setup, per package

npm cannot create a package over OIDC: a trusted publisher can only be configured on a package
that already exists ([npm docs](https://docs.npmjs.com/trusted-publishers/)). So each package
needs one manual first publish, and then never again:

1. `npm login` as a maintainer of the `@fullstackhouse` scope.
2. `node scripts/set-release-version.mjs 0.1.0`
3. `yarn build:packages`
4. `cd packages/durable-work && npm publish --access public`
5. `cd ../data-sync-durable && npm publish --access public`
6. On npmjs.com, for **each** package: *Settings → Trusted publisher* → GitHub Actions,
   repository `fullstackhouse/open-mercato-durable`, workflow `ci.yml`.
7. `git tag v0.1.0 && git push --tags`, so semantic-release continues from there.
8. In the repository's *Settings → Secrets and variables → Actions → Variables*, set
   `NPM_RELEASE_ENABLED` to `true`.

From then on every merge to `main` publishes by itself.

Step 7 is not optional bookkeeping. Verified against this history: with no tag on the branch,
semantic-release computes the first release as **1.0.0**; with `v0.1.0` present it picks up from
0.1.0 and releases nothing until a `feat` or `fix` lands. The tag is what keeps the line in 0.x.

Step 8 is why the pipeline is green in the meantime. Until each package exists on npm, an
automated release could only fail, and a permanently red pipeline is how people learn to ignore
one.

## Checking what a merge would release

    yarn release:dry-run

Reports the version it would pick and the notes it would write, and publishes nothing.
